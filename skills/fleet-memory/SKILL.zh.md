# 用项目文件接续工作

接手一项工作，先用项目卡、对应岗位的交接和实际交付核对做到哪一步，再按决定编号查上次为什么这么定。工作中遇到的阻碍当场留在机会表里，供下一轮决定试哪条规矩、由谁复验。

只在读者指定项目里读写工作记录。项目卡在根目录 `AGENTS.md`，根目录 `CLAUDE.md` 用 `@AGENTS.md` 引用；交接、决定和其他协作文件在 `fleet/`，任务和交付也只指向项目内文件。不读写项目以外的任何记忆目录。以项目根目录为工作目录。

## 让舰队自己改进

1. 工作卡住、人被打扰、同一件事反复要纠正时，当场把事情和证据位置记进 `fleet/机会.md`。旧项目缺这份文件时，用[机会表模板](../fleet-setup/templates/zh/机会.md)补上。每条按实际进度标为“想法”“定了没做”“在试”“已验证”或“已撤回”。
2. 每周过一次机会表，数一数同类问题发生了几次。项目已有 `fleet/合作方式.md` 时，一起看里面记的人的偏好。同类问题出现至少两次，或审批流中有权的岗位明确同意提前试一次，才选一条小范围试改。没有遇到真问题就沿用原规矩，不为展示硬造问题。
3. 给试改分配一个决定编号，在机会表和 `fleet/决定.md` 中用同一编号串起原审意见及其出处、试行的规矩、适用范围、复验人和结果。没有原审意见时，如实注明，并指回最早记录问题的交接或机会条目。先写清怎样算见效，结果先记“待复验”。试行规矩先由同伴互审，再换一家厂商的模型复核。两级审核通过后，由审批流里有权的岗位决定是否试行，把决定记在同一编号下。决定试行就按约定范围做，标为“在试”。人可以随时参与判断，方向、对外承诺、花钱和删东西由人定。
4. 复验人按原定判据核对试行后的交付，把结果和证据位置追加到同一编号下。还没遇到适用的任务或证据不足时，保持“在试”，记下下次由谁用什么证据复验。由审批流里有权的岗位按复验结果决定保留或撤回，记下理由。见效的标为“已验证”，把通过审核的规矩写回项目规矩和相应技能，注明替代了哪条。没效就恢复原做法，在机会表的状态列标“已撤回”，在决定记录的同一编号下用一句话写明撤回原因。下一位接手者凭编号就能查到这次取舍。

## 核对状态并交接

重启、换会话或上下文压缩后，先读根目录 `AGENTS.md`，再读 `fleet/交接.md` 中交给本岗位或本任务的最新一节，和实际状态核对，再动手；按文件地图读这次任务需要的原则、成员和决定。核对实际文件、输出和任务状态：交接写“进行中”不证明仍在执行，写“完成”不证明已经合格。发现不一致时先记录看到的事实，再决定从哪一步续接；避免重复运行已完成的动作。

人要续接时（比如说“接着干”），核对完，回话最前面先给这三行，再往下做：

```text
上次停在：……
交接以来做完：……（跑完、收到、审过分开写）
在等你定：……
```

哪一行没有内容，就写“没有”。三行都以文件和实际状态为准，里面的日期、时刻先取系统时间，不估。

压缩后的摘要只当线索，不当依据。摘要可能丢掉长期规矩、正在运行的任务和文件惯例，不能凭它直接续做。先读项目卡和匹配的交接，核对过再动手。交接按岗位或任务定位，不按时间直接取最后一条；分不清是不是自己的，就列出有关章节标题，说明选错可能重复做事，请人在这里只回要续接的一个标题或岗位和任务。先和项目卡及实际文件核对，再从那一步继续。宿主支持的话，让它在上下文压缩后自动提醒先读文件并核对。

项目卡保持一页：目标与规矩、正在做什么、等人定什么、文件地图。项目卡只由项目经理岗位维护，其他岗位通过交接和决定记录提出改动。正文只更新根目录 `AGENTS.md`；新建的 `CLAUDE.md` 只保留一行引用。已有这两个文件时，保留其他内容，只维护“AI 舰队项目卡”一节和对应引用。项目卡第一行写：重启、换会话或上下文压缩后，先读项目卡和交给本岗位或本任务的最新交接，和实际状态核对，再动手；收工或上下文快满时，先写交接。已有文件中的该节把这句话放在正文第一行。只放恢复工作必需的信息，历史留在交接和决定中。

要人定、要人回答的事，记进项目卡“等我定”（其他岗位经交接提出，由项目经理记入）：每条开头写日期（`YYYY-MM-DD`），写明哪个岗位在等、要人做什么、倾向、理由、需要谁决定。不卡住手头工作的，攒成一批，到一个停顿点（比如一步做完、收工前）一次列给人，请人逐条回；卡住工作的，当场问。等人回的时候，那一件先放着，接着做不受它影响的活，不让整条线跟着等。搭建时照 fleet-setup 一次问一件。人回了，当场把结论记进决定记录，再从“等我定”里拿掉。

人的重要决定、新定的规矩、刚启动的后台任务，发生时就写入决定记录或交接；不要攒到收工。后台任务同时写明任务标识、运行证据、成功和失败的识别方法，以及续接方式。复验见效的改动也写进下次做同类事会先看到的地方，比如任务书模板、名册或项目卡。

重要交接写进接手岗位或任务会读的文件，并在项目卡或接手方的任务书中写明位置。消息只用于及时知会；消息通道受阻时，交接照常落文件，继续已获授权且不受阻的工作，不等人开通。

可选：工具支持定时任务时，设置定时醒来，醒来先读项目卡和匹配交接，再核对实际状态。每次结束前把交接写入文件，供下次醒来续接。定时只负责叫醒（工具没开、电脑睡着时不会醒）；节点做完后重新排活、等人的事分流、出了错告诉人，靠成员照本节做，本包不替你盯。醒来先接手上排着的下一件，再看外面有没有新动静；真没有能做的，在交接里写明为什么、几点再看，告诉项目经理排活（项目经理就告诉人，并提一两件可以接着排的活），不要只等。

收工或上下文快满时，先向 `fleet/交接.md` 末尾追加一节，每节标题写明接手岗位和任务，用 [交接模板](../fleet-setup/templates/zh/交接.md)：做到哪、接下来排着的几件（排到节点之后，写明第一件卡住时先做哪件）、卡在哪、谁接和何时接；写清成功、失败各走哪条路，附能直接运行的恢复命令及其工作目录。命令涉及重跑或外部动作时，先写核对条件，不能把再次执行当成默认动作。没有在运行的任务就如实写没有。收工时核对当场记录是否齐全、状态是否有变化；项目经理核对项目卡。

`fleet/决定.md` 只追加，用 [决定模板](../fleet-setup/templates/zh/决定.md) 写日期、谁定、定了什么、为什么和依据。改做法、改规矩的决定，依据里写清五件事：这么改的好处、坏处、怎么减轻坏处、不改会怎样、以后怎么判断改得成不成；小改动一两句就够。旧决定被替代时加一条新记录，指向旧条目；保留原文，不改写成从未发生。交接和决定里的日期、时刻，写之前先取系统时间（比如运行 `date`；Windows 上用 PowerShell 的 `Get-Date`），不凭对话估。

写完后重新打开记录，核对项目内相对路径和命令输入确实存在，指定接手岗位。交接中的判断标出看到的、推断的、猜的；缺证写证据不足。完成后交回新增章节和待办。无法确认既有决定、恢复命令会跨越授权边界时，保留当前状态，列出具体冲突和建议，按审批流找到能决定这一项的人或岗位，请其解决这项冲突或明确确认所列动作及范围；先按项目规矩核对回复并记录，再只读核对命令输入，从中断处续做。仍有不清楚的，只问下一项缺失信息。不索要密钥或密码；定方向、对外承诺、花钱、删东西先由人点头。
