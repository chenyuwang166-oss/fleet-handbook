# 一起定舰队的价值观

从成员实际遇到的一次取舍出发，问下回遇到同类事该依哪条原则判断、依据是什么。把决定和实质分歧一起留下，让下一个接手的人能查到当时的理由。

只读写读者指定项目内的工作文件。先读根目录项目卡、`fleet/成员.md`、审批流，以及已有的原则、价值观和决定记录。保留已确认内容，修订前先查当时的理由。缺少名册、项目经理或这类事项的授权时，说明第一项缺什么、为什么要。按情况只问一个参与岗位、哪个岗位任项目经理，或审批流这类事项交给谁定。先和项目记录核对，再问下一项。

按以下顺序进行：

1. 请每个成员各提几条。每条写清：建议的条目、对着 AI 成员的哪种毛病、依据是什么、具体做什么和不做什么。依据区分看到的、推断的、猜的；没有实际观察就如实说明。按项目已有调用方式收集，保留提案来源，不代替未参与的成员发言；缺交的列出来。
2. 由项目经理汇总。合并重复项，保留实质分歧，写清候选条目的取舍和理由。条目少而深，行为能被核对。不替读者定价值观，也不把任何现成价值观作为默认值。
3. 将每条候选、依据、未解决的分歧和项目经理的倾向先交同伴互审，再换一家厂商的模型复核，记下两次审核意见。缺哪一级审核，就保留待审状态。涉及方向的由人定，人也可以随时参与判断。既定方向内的行为条款，由审批流里有权的岗位定。一次请决定者确认一条的准确文字，或指出要改哪里。没有明确决定的条目继续待定。
4. 确认后写入 `fleet/价值观.md`，可从[空模板](../fleet-setup/templates/zh/价值观.md)起步。每条写明对着哪种毛病、做什么、不做什么、适用范围及确认依据。未确认的只放候选区，不能当作生效条目。
5. 向 `fleet/决定.md` 末尾追加本次决定，记录采纳或未采纳的理由、不同意见及处理结果，并与价值观条目相互指向。不同意见没有得到答复就写未解决，不改写成一致同意。修订时引用旧决定，保留历史。

写完重新打开文件，检查每条已确认的价值观是否写明做什么、不做什么，是否有两级审核记录及决定者的确认。核清候选和生效状态，检查引用能否在项目内找到。交回已确认条目、待确认项、未收齐的提案及不同意见所在位置。还有待办时，写明下一位审核者或决定者，以及要解决的具体问题。收提案时若需人协助接通成员，按 fleet-dispatch 带着人补好当前这一步，核对回复后续收。不索要密钥或密码。对外承诺、花钱和删东西也须先由人点头。
